The problem

As a company admin, I need to register my company and complete a subscription payment, so that my account activates immediately on success, remains accessible while awaiting async payment confirmation, and lets me retry a declined payment without having to start over.
Scope note:  card details are never stored — they go directly to Stripe. 3DS state handling is built; completing the redirect requires Stripe.js (no frontend in this slice).

Integration: Stripe Payments Stack: Java 21 · Spring Boot · PostgreSQL Live on: Railway
The three outcomes drive the interesting engineering: immediate activation is straightforward — it's the async webhook path and failure recovery that require careful design. 3DS: the state machine handles ACTION_REQUIRED correctly, but actually completing the redirect needs Stripe.js. "Without starting over" means the Company record persists through payment failures — retry creates a new session, not a new company.

The slice I chose is the full onboarding flow: register → initiate payment → receive webhook → activate. I used hexagonal architecture because the core business rules — state transitions, retry limits, aggregate invariants — should be verifiable without a database, without Stripe, and without Spring. The architecture enforces that. Every boundary is crossed through an interface; infrastructure implements those interfaces, never the other way around.

The REST API is the inbound boundary — how clients drive the system. The webhook endpoint is also inbound but owned by Stripe, not our clients. The two columns below show the outbound boundaries — what the system depends on. The common thread: the domain defines what it needs through an interface, infrastructure delivers it. The domain never imports a Stripe class, a JDBC class, or a Spring class — that's what keeps it testable in plain Java. On the MockPaymentGateway: because it implements the real interface, the compiler tells you immediately if the mock is out of sync with production. You can't accidentally test against something that no longer matches real behaviour.
03 · Failure Scenarios & Recovery

What breaks and what the backend returns

Scenario Backend response Company status
Invalid / missing fields 400 · {"message": "Validation failed: field: reason; ..."} No change
Stripe API unavailable 503 · {"message": "Payment service unavailable. Please try again later."} INCOMPLETE
Card declined Stripe webhook processed · 200 to Stripe ACTIVATION_FAILED
3DS required Stripe webhook processed · 200 to Stripe ACTION_REQUIRED
Retry limit reached (3) 422 · {"message": "Maximum payment attempts reached. Please contact support."} REQUIRES_SUPPORT
Duplicate webhook 200 empty body — event ID already in processed_stripe_events, no processing No change
Webhook before session commits 404 to Stripe · Stripe retries automatically up to 72 h Delayed · resolves on retry

There is no frontend in this slice. The HTTP response codes, error messages, and company statuses are all intentional signals — a client uses the response code to handle errors immediately, and polls GET /api/v1/onboarding/{sessionId}/status to track async state changes and decide what to render.

The state machine on the Company aggregate is what makes failure handling clean — every invalid transition throws a domain exception, so there's no way to accidentally activate a company whose payment failed. The retry limit is a production safety measure: unlimited retries would trigger Stripe's card-hammering detection and damage the account's risk score. Three attempts then escalate to support.
04 · Tradeoffs & Decision-Making

Key decisions and why

OnboardingSession — separate aggregate
Each retry creates a new session → Company history is never mutated
Alt: entity inside Company · simpler, but muddies audit trail
JDBC over JPA
Explicit SQL · no dirty-check surprises · aggregate boundaries stay clean
Alt: JPA · less boilerplate, but fights DDD at aggregate edges
Domain events — not implemented
No consumers exist yet — the natural first consumer would be a notification service (e.g. alert the admin on payment failure or retry exhaustion)
Once consumers exist: Transactional Outbox for guaranteed delivery
Client-supplied ipCountry
No geolocation infra needed. Risk: client can claim cheaper region
Alt: server IP lookup (MaxMind) · tamper-proof, adds infra dependency

To a PM: "We chose the simpler approach in each case and named the risk explicitly. Each has a clear upgrade path and the hexagonal boundary means swapping an implementation is a one-class change."

For each tradeoff I tried to identify: what the simpler choice gives us, what it costs, and what the upgrade path looks like. The hexagonal boundary is the key enabler — because infrastructure implements a domain-owned port, swapping from client ipCountry to MaxMind, or adding a Transactional Outbox when events are eventually built, requires no changes to the domain or application layers.

INTENTIONALLY LEFT OUT

Frontend / Stripe.js — UI decisions not made yet
Auth / JWT — out of scope for MVP; payment & status endpoints need bearer token protection once built
Domain events — not implemented; no consumers exist yet. First candidate: notification service for payment failures and retry exhaustion
Rate limiting — ops concern, add at gateway layer

The slice criteria: a complete path through the system with one integration explored in depth. Register → pay → activate is that path. Everything excluded has a clear hook to add it without touching domain logic.

The hardest scope call was auth. Onboarding is a pre-auth flow — the user doesn't have an identity yet, so issuing a JWT on registration would be the wrong design. Auth belongs to a separate bounded context. The payment and status endpoints are protected by the unguessability of the sessionId UUID for now, and the design doc notes exactly which endpoints need bearer tokens once the auth slice is built.
06 · AI Tool Usage

Where AI helped — and where I pushed back

Used Claude as a collaborative design partner throughout — architecture, code generation, documentation drafting. Every output was reviewed before being accepted.

Risk: H2 in-memory test database
AI scaffolded integration tests using H2. H2 and PostgreSQL have different SQL dialects and type handling — tests passing on H2 can mask failures that only surface in production. Replaced with Testcontainers (postgres:16-alpine) so tests run against the real engine.
Risk: status enum leaked payment concepts
AI named states PENDING_PAYMENT / PAYMENT_FAILED. These tie the domain model to a specific integration. Renamed to PENDING_ACTIVATION / ACTIVATION_FAILED — the company describes its own lifecycle, not what Stripe returned.
Risk: amountInCents is currency-specific
AI generated amountInCents. "Cents" doesn't apply to JPY (no minor unit) or KWD (3 decimal places). Corrected to amountInMinorUnits — the ISO 4217 standard term.
The theme across all three: AI produces plausible-sounding output that passes a quick read but fails on precision. H2 tests compile and run — you'd only discover the problem in production. The naming issues would have baked wrong assumptions into the domain model permanently. The verification step was reading the actual spec (PostgreSQL docs, ISO 4217) rather than trusting the AI's confident-sounding suggestion.
